# Coder and AWS Nitro Sandboxes

| Field | Value |
|---|---|
| Date generated | 2026-11-10 |
| Last reviewed | 2026-11-10 |
| Category | Complementary |

*(AWS announced Nitro Sandboxes on 2026-11-09 for [Amazon EKS pods, Amazon ECS tasks, and lightweight VMs on EC2](https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/). This comparison treats the runtime as complementary: it supplies an isolation boundary underneath workload orchestration, not an integrated development platform. AWS also publishes agent and IDE blueprints that create an indirect, build-versus-buy alternative to Coder. This page focuses on EKS and Kubernetes-based Coder workspaces. A Coder–Nitro configuration is a proposed integration, not established interoperability.)*

## One-Line Positioning

Nitro Sandboxes gives opted-in AWS workloads their own hardware-isolated VM, while Coder is a self-hosted platform for provisioning and governing environments for developers and coding agents; the runtime could complement Coder on EKS, while AWS's assembled agent and IDE blueprints offer a starting point for teams building their own platform.

## Strategic Themes and Patterns

- **Relationship.** Complementary at the runtime layer, with indirect competition through a do-it-yourself platform. AWS describes the EKS integration as “a Kubernetes RuntimeClass, not a new API” that “slots underneath” existing tools ([AWS launch blog](https://aws.amazon.com/blogs/containers/aws-nitro-sandboxes-hardware-enforced-workload-isolation-on-amazon-eks/)). Unlike a separate environment platform, the runtime can be selected by the controller that already creates a pod. That makes it a candidate for layering beneath Coder, not evidence of a validated integration.
- **Where the two meet in a buying decision.** AWS positions Nitro Sandboxes for coding agents, cloud agents with self-hosted tool execution, and browser-based VS Code and Kiro CLI workspaces. Its [sample repository](https://github.com/aws-samples/sample-eks-nitro-sandbox) includes agent adapters, warm pools, CI builds, and a browser IDE. The [developer-agent blueprint](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/main/examples/ai-agents/coding-agents-for-developers/README.md) goes further: it provides a web app, agent selection, templates, persistent session storage, and open/restore/delete operations. These are substantive platform building blocks, not a managed enterprise development platform. The blueprint explicitly describes its demo sign-in as a picker, not authentication.
- **Choice, Control, Consistency.** Coder retains its broader cloud-neutral platform model, but a template adopting Nitro Sandboxes inherits AWS-specific runtime and operational constraints. On Choice, Nitro Sandboxes is available on supported AWS infrastructure, while Coder supports cloud, on-premises, and air-gapped deployments ([Coder Message House](../company/message-house.md)). On Control, AWS supplies IAM, runtime policies, Kubernetes access controls, and logging components; customers configure and integrate them. Coder adds centralized workspace access and lifecycle management, plus the applicable licensed governance features. On Consistency, Coder applies a common template-based baseline to developer and agent environments ([Coder Workspaces message house](../products/coder-workspaces/message-house.md)). Kubernetes manifests can also standardize workloads; the distinction is the surrounding user-facing platform, not whether a pod specification can define a repeatable environment.
- **Build versus buy.** AWS's [coding-agent example](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/main/examples/getting-started/coding-agent/README.md) combines a Bedrock-scoped IAM role, a repository-scoped GitHub token, an agent image, and egress policy. Turning these and the larger blueprints into an enterprise service requires identity integration, environment management, policy configuration, audit retention, and ongoing operation. Coder provides an integrated platform for those concerns, but customers still configure their templates, infrastructure policies, authentication, and budgets. This is the build-versus-buy distinction described in [Why Coder](../company/why-coder.md), not a claim that AWS lacks the underlying controls.
- **Proposed combination.** Coder's [Sysbox example](https://coder.com/docs/@main/templates/extending-templates/docker-in-workspaces#use-sysbox-in-kubernetes-based-templates) demonstrates the Terraform Kubernetes field `runtime_class_name`; AWS documents the corresponding Kubernetes field `runtimeClassName` with the value `isolated-sandbox`. Those mechanisms suggest a configuration to evaluate in a compatible Coder template. The cited public sources do not establish vendor-validated Coder–Nitro interoperability. Provisioning, workspace connectivity, network enforcement, storage, lifecycle operations, and prebuild claiming need validation; changing the runtime string alone is not sufficient.

## Coder's Strengths Here

- **An integrated environment platform.** Coder's Terraform templates define infrastructure and environment configuration for developer and agent workspaces on VMs, Kubernetes, or containers ([Coder Workspaces message house](../products/coder-workspaces/message-house.md)). Nitro Sandboxes supplies the VM boundary for a workload; AWS's additional samples assemble orchestration and user-facing features above it.
- **Central control of workspace definitions.** AWS says the runtime “is not designed to run untrusted pod specs” and treats pod submission as a privileged operation ([EKS security model](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)). With Coder Premium's [template permissions](https://coder.com/docs/@main/templates/template-permissions), template administrators control the infrastructure definition and users granted Use can create workspaces from it. Safe parameters, Kubernetes RBAC, and admission policy still matter; template permissions do not replace cluster controls.
- **Native agent activity associated with a user.** [Coder Agents](https://coder.com/docs/@main/coder-agents/architecture) associates activity with the initiating Coder user and can use configured external Git authentication. Git commit author and committer metadata still depend on the workspace's [Git configuration](https://coder.com/docs/@main/coder-agents/platform-controls/template-optimization#git-identity). AWS's example also has an attributable GitHub credential: its pull request appears under the token owner's identity unless a GitHub App token is used. Coder's distinction is integrated identity and workspace management, not exclusive access to person-attributable Git credentials.
- **Governance of routed model traffic.** AI Gateway authenticates clients with a [Coder API token](https://coder.com/docs/@main/ai-governance/ai-gateway/auth), supports [Amazon Bedrock and other providers](https://coder.com/docs/@main/ai-governance/ai-gateway/providers), and applies configured [spend budgets](https://coder.com/docs/@main/ai-governance/ai-gateway/cost-controls). For supported intercepted APIs, its [audit records](https://coder.com/docs/@main/ai-governance/ai-gateway/audit) include prompts, requested tool calls, token usage, and available model reasoning, organized into sessions and threads. Tool responses and model-produced inference text are not retained by that audit facility; [passthrough endpoints](https://coder.com/docs/@main/ai-governance/ai-gateway/reference#supported-apis) are not audited. Budgets are approximate because in-flight requests can exceed a threshold, and users without configured budgets have unlimited spend.
- **Cloud-agent execution on managed workspaces.** [Agent Relay](https://coder.com/docs/@main/agent-relay), a Premium beta, connects supported Claude Code and Cursor cloud sessions to Coder workspaces. Personal sessions normally map to a Coder user by email; Claude Tag channel sessions use a configured shared identity rather than the person who tagged Claude ([Slack integration](https://coder.com/docs/@main/agent-relay/slack#claude-tag-channel-sessions)). Relay governs execution infrastructure and lifecycle, not provider-side inference. It does not give Coder access to model selection or token usage, and AI Gateway is not in these integrations' inference path ([Claude Code FAQ](../products/coder-agent-relay/claude-code-faq.md), [Cursor FAQ](../products/coder-agent-relay/cursor-faq.md)).
- **Ready workspace pools.** Premium [prebuilt workspaces](https://coder.com/docs/@main/templates/extending-templates/prebuilt-workspaces) maintain and replenish pools for configured presets. A compatible Nitro-based template might use them to reduce user-visible startup time, but claiming must preserve the running resources rather than recreate the pod. This is a proposed use, not a measured Nitro integration benefit or an equivalent to every AWS warm-pool implementation.
- **Infrastructure choice.** Coder supports cloud and on-premises infrastructure, [air-gapped deployment](https://coder.com/docs/@main/install/prepare/airgap), and Linux, macOS, and Windows workspaces ([Coder pricing](https://coder.com/pricing)). This does not mean all operating systems or every Coder integration work in Nitro EKS pods. Agent Relay still needs connectivity to its cloud provider.

## AWS Nitro Sandboxes Overview

- **What it is.** Each sandboxed EKS pod runs in a lightweight VM with its own guest kernel. AWS describes it as a Firecracker microVM running as a first-level guest on the Nitro Hypervisor, not through nested virtualization ([EKS user guide](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)). Only opted-in workloads receive this runtime boundary.
- **EKS modes and trust model.** Isolated mode treats the parent instance as trusted and the guest workload as untrusted. Confidential mode also treats the parent as untrusted. Protecting secrets requires attestation verification, typically a KMS policy that checks the expected policy and guest-image identity; selecting confidential mode alone is insufficient. Plaintext logs, mounted secrets, storage, and application behavior also need protection ([EKS confidential setup](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html), [security model](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)).
- **Architecture and operations.** An EKS pod selects `isolated-sandbox` or `confidential-sandbox` through `runtimeClassName`. AWS documents Pod Identity, EBS/EFS storage, VPC CNI networking, and CloudWatch integration. Compatibility has qualifications: confidential mode denies exec, stdin, and process listing by default, with specific exec commands configurable through Cedar policy ([observability](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)). Port forwarding requires a network-enabled sandbox and a server listening on the pod IP or all interfaces, not only loopback ([limitations](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)). Shared host resources have configurable [throttles](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html).
- **Ecosystem and target uses.** AWS says it validated Claude Code, Codex, Strands, and OpenCode, built CI/CD support with GitLab Runner, and validated Temporal orchestration. It points to Kubernetes SIG agent-sandbox for warm pools. Its target uses include agentic AI, multi-tenant SaaS, regulated workloads, and privileged CI/CD builds ([launch blog](https://aws.amazon.com/blogs/containers/aws-nitro-sandboxes-hardware-enforced-workload-isolation-on-amazon-eks/)). These are AWS-described validations and use cases, not named customers or compliance certifications. The [browser IDE sample](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/main/examples/agent-sandbox/ide/README.md) uses Coder's open-source code-server, not the Coder Workspaces platform.
- **Deployment model.** On supported EKS Auto Mode clusters, sandbox support is included. Other EKS node groups need a sandbox-enabled custom AMI and Nitro Enclaves enabled in the launch template ([isolated setup](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)). ECS supports Nitro Sandboxes through ECS Managed Instances, not its EC2 or Fargate launch types ([ECS getting started](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ict-getting-started.html)). Direct EC2 use is a self-managed integration with the customer's AMI and orchestrator; its primitive modes are confidential and direct, distinct from EKS's workload profiles ([EC2 guide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html)).
- **Availability.** AWS's sources disagree as of 2026-11-10. The [What's New announcement](https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/) and EKS launch blog say all commercial regions; the EKS user guide says US commercial AWS Regions. Confirm the target region and supported instance type with AWS rather than treating the broader announcement as a deployment guarantee.

## Coder Overview for This Comparison

- **Coder Workspaces.** Self-hosted, Terraform-provisioned environments for developers and agents ([message house](../products/coder-workspaces/message-house.md)). A workspace can contain more than one infrastructure resource; a per-pod VM boundary is not necessarily a single boundary around the entire workspace.
- **Workspace network policy.** Templates configure infrastructure controls on traffic originating in workspaces. Agent workspaces inherit the effective connectivity of the template and underlying infrastructure; Coder does not make them default-deny automatically. Native Coder Agents can execute workspace tools with egress restricted to the control plane and, when needed, Git, with allowances for additional workflow dependencies ([architecture](https://coder.com/docs/@main/coder-agents/architecture#workspaces-can-be-fully-network-isolated), [template optimization](https://coder.com/docs/@main/coder-agents/platform-controls/template-optimization#configure-network-boundaries)). Workspace policy does not constrain tools running in the control plane or at a model provider. Relay workspaces also need their cloud provider's endpoints.
- **Coder Agents and isolation.** The native agent loop runs in the Coder control plane and executes workspace tools over the workspace connection. Coder documents a separate-agent-pod pattern with its own network policy, while describing sandboxing as early-stage. Its [isolation guide](https://coder.com/docs/@main/coder-agents/platform-controls/agent-isolation) warns that Kubernetes can accept a NetworkPolicy without enforcing it and that the Amazon VPC CNI pattern should use Deployment-managed rather than standalone pods. Effective enforcement must be tested, not assumed from accepted configuration.
- **Separate audit scopes.** Coder's [audit log](https://coder.com/docs/@main/admin/security/audit-logs) records supported platform operations, including workspace lifecycle events. AI Gateway audits supported model requests routed through it. Agent Relay logs its own dispatch, identity-resolution, build, and cleanup operations; it does not collect conversation transcripts or provider CLI output ([Relay monitoring](https://coder.com/docs/@main/agent-relay/monitoring)). These are distinct capabilities, not a comprehensive record of all shell commands, file changes, network traffic, or cloud-agent inference.

## Where AWS Nitro Sandboxes Is Strong or Coder Has a Gap

- **A documented VM boundary for each opted-in pod.** Nitro Sandboxes supplies a separate guest kernel and a hypervisor-enforced isolation boundary while preserving Kubernetes orchestration ([EKS user guide](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)). Coder templates provision infrastructure; they do not by themselves turn an ordinary Kubernetes container into a hardware-isolated VM.
- **Confidential workload primitives.** AWS provides attestation and policy mechanisms for a threat model that includes an untrusted parent instance. Those guarantees depend on correctly configured verification and application/storage design. A Coder integration would need its own threat-model review: blocking Kubernetes exec does not establish that Coder's in-guest daemon or control-plane access is blocked.
- **Privileged build examples on EKS.** AWS publishes an [EKS Docker-build blueprint](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/main/examples/ci-cd/docker-builds/README.md) using `privileged: true` inside an isolated sandbox, with privilege confined to the guest. This is affirmative AWS example evidence, not proof that Coder's particular Docker-sidecar or Sysbox-dependent templates work unchanged. Coder's [privileged-container warning](https://coder.com/docs/@main/templates/extending-templates/docker-in-workspaces) concerns the conventional host-sharing pattern; it is not evidence of a Nitro VM escape.
- **No separate Nitro Sandboxes fee.** AWS offers the capability at no additional charge, while underlying infrastructure and service charges remain. Teams already operating AWS orchestration and governance can build on that investment without buying a separate sandbox license ([What's New](https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/)).

## Known Limitations and Integration Constraints

- **AWS and cluster prerequisites (as of 2026-11-10).** EKS requires Kubernetes 1.36 or later and supported Nitro-based instances. Outside Auto Mode, the custom-AMI path requires the sandbox runtime; Amazon Linux 2023 needs kernel 6.18.51 or later ([EKS guide](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html), [AMI guide](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-ami-create-update.html)). This boundary does not extend to Coder workspaces on other clouds or on-premises.
- **An EBS volume cannot be shared across sandboxed pods (as of 2026-11-10).** This is not a one-volume-per-pod limit. AWS recommends `ReadWriteOncePod` for EBS and supports EFS for shared read-write storage across pods, with EFS CSI add-on 3.5.0 or later ([storage](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-storage.html)). Coder's two-pod isolation example shares a `ReadWriteOnce` PVC. If that PVC is EBS-backed, the design requires a different storage arrangement; EFS is a documented AWS option, not a validated adaptation of that Coder example.
- **No GPU passthrough or host networking (as of 2026-11-10).** GPU and other device passthrough are unsupported at launch, and pods with `hostNetwork: true` fail to start ([limitations](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)). Templates requiring these features need a different runtime or redesign.
- **The no-network annotation prevents normal Coder connectivity (as of 2026-11-10).** AWS's network-isolated annotation removes the ordinary network interface, DNS, and Pod Identity. A normal Coder workspace daemon therefore cannot establish its required control-plane connection. This is an annotation, not a third EKS runtime mode, and the runtime's vsock channel remains; it is not an absolute no-communication guarantee ([network isolation](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html)). A proposed Coder configuration needs network connectivity and appropriate egress controls.
- **Bandwidth and density require sizing (as of 2026-11-10).** Default ingress and egress bandwidth are each 100 Mbps, configurable rather than fixed maxima ([resource isolation](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)). EKS imposes two caps: aggregate sandbox vCPU allocation and sandbox count are each limited to five times node vCPUs, with the count cap halved on CPU-overcommit instance types. Memory can constrain density sooner. On SMT instances, cross-sandbox core scheduling affects effective concurrency; do not interpret it as a universal 50% performance reduction for every workload ([limitations](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)).
- **Sample startup timings are not a Coder benchmark (as of 2026-11-10).** AWS's [warm-pool example](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/main/examples/getting-started/warm-pool/README.md) reports three runs on an already-running node with cached images: 3.2–3.7 seconds for a sandboxed pod versus 0.8–0.9 seconds for an ordinary pod, measured after create returned until Ready. New-node provisioning and image pulls are excluded. These are sample observations, not a service commitment or an end-to-end workspace startup measurement.
- **Confidential integration is more than runtime selection (as of 2026-11-10).** Policy must match the final pod specification, including admission-time mutations, and secret release needs correctly configured attestation verification ([confidential setup](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)). Dynamic workspace configuration, guest access, credentials, and persistent data need an explicit design before claiming confidentiality for a Coder session.
- **Customers integrate the governance components (as of 2026-11-10).** AWS supplies Cedar runtime policies, Kubernetes RBAC/admission, workload IAM, and logs. [EKS control-plane audit logs](https://docs.aws.amazon.com/eks/latest/userguide/control-plane-logs.html) can record actions by users and system components; [Bedrock invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) can capture supported model requests and responses when enabled. These are not an automatically assembled per-person developer/agent governance experience. Conversely, the [GuardDuty runtime-monitoring limitation](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)—its host agent cannot observe activity inside the sandbox—is not evidence that all application, model, or network logging is unavailable.

## Common Questions

- **Does Nitro Sandboxes replace Coder?** Not as an isolation primitive. Nitro changes the boundary around a workload; Coder supplies a user-facing platform for environments, access, and lifecycle, with governance features according to license and configuration. AWS's agent/IDE reference stack can be the basis for a platform a team builds and operates instead. The relevant decision is a runtime choice, a build-versus-buy choice, or both—not an established feature-for-feature replacement.
- **Can Coder workspaces run inside Nitro Sandboxes?** The documented runtime-class mechanisms suggest a candidate EKS configuration, but they do not establish interoperability. Validate agent connectivity, IDE access, persistence, policy enforcement, create/start/stop/delete, and any prebuilt-workspace claim flow. GPU and host-network requirements conflict with the documented runtime. Shared EBS across pods requires redesign; shared EFS is supported by AWS. Confidential mode needs a separate security and policy assessment.
- **AWS already has an agent example with Bedrock, GitHub, and egress policy. Why add Coder?** Coder offers an integrated workspace platform and configured user access, rather than leaving the team to operate a collection of blueprints. Do not overstate either side's security defaults. AWS's [example](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/main/examples/getting-started/coding-agent/README.md) permits DNS and Pod Identity alongside Bedrock/GitHub, notes that public GitHub repositories remain readable, and documents that domain rules can allow other names sharing approved addresses. Coder templates likewise need deliberate credential and network configuration; adding Coder alone does not establish those restrictions.
- **We use Claude Code or Cursor cloud sessions. Do we need Nitro Sandboxes or Agent Relay?** They address different concerns: workload isolation versus provisioning and governing the execution environment for a provider's session. Agent Relay is a Premium beta with provider-plan and version requirements in its [documentation](https://coder.com/docs/@main/agent-relay). Session identity has provider-specific exceptions, and cleanup is not synonymous with closing a chat: Cursor has an idle-release setting, and Relay does not delete stopped workspaces ([Cursor lifecycle](https://coder.com/docs/@main/agent-relay/cursor#workspace-lifecycle), [Relay setup](https://coder.com/docs/@main/agent-relay/setup#workspace-lifecycle)). A Nitro-backed Relay template is a proposed combination requiring validation. Relay does not provide AI Gateway visibility into provider-side inference.
- **What audit trail do we get?** AWS supports container logs and metrics, Kubernetes control-plane audit, optional Bedrock invocation logging, and KMS attestation evidence in CloudTrail for the documented [ECS confidential flow](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ict-confidential-policy-configuration.html). Coder's platform audit records supported operations such as workspace creation. AI Gateway records supported intercepted model requests, including requested tool calls—not proof of their execution or their results. Relay provides execution-infrastructure and lifecycle visibility, not model transcripts or token accounting. Select and configure the controls needed for the actual workflow rather than assuming either stack supplies a complete activity record.
- **We aren't only on AWS. Does this matter?** Nitro's boundary is AWS-specific. Coder's broader infrastructure choice remains, but workspaces elsewhere need their infrastructure's own isolation design. An air-gapped Coder deployment does not make AWS services or cloud-agent Relay sessions available without their required connectivity.

## Pricing and Packaging

- **Nitro Sandboxes has no separate charge.** AWS says “at no additional charge.” ECS customers still pay for underlying EC2 instances and the standard ECS management fee ([What's New](https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/), [ECS considerations](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ict-considerations-and-limitations.html)). The documented EKS runtime classes reserve 256 MiB per isolated pod and 512 MiB per confidential pod, in addition to workload resources ([AMI guide](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-ami-create-update.html)). Density, storage, logging, and idle warm capacity affect infrastructure cost.
- **Coder licensing and agent usage are distinct.** [Coder pricing](https://coder.com/pricing) lists free, open-source Community; annually per-user Premium without a published numeric list price; and custom-priced AI Premium. AI Governance, including AI Gateway, is included with Premium. Community and Premium allow up to five simultaneously active Coder Agents deployment-wide. AI Premium removes that concurrency cap, with usage drawing from allotted Agent Hours. Prebuilt workspaces, template permissions, and audit logging are Premium capabilities; Agent Relay also requires Premium. See [Packaging](../company/packaging.md) for the narrative behind the tiers.
- **The costs combine rather than substitute directly.** A proposed Coder-on-Nitro deployment would combine applicable Coder licensing and Agent Hours, customer-operated infrastructure, and provider inference costs. No separate Nitro fee does not mean free workspace infrastructure, free model usage, or equivalent total cost across configurations.
